# 0009. Сущность «автомобиль» упразднена: параметры и госномер — снимок записи

- **Статус:** Accepted
- **Дата:** 2026-09-09
- **Связанные ADR:** 0004 (снимок параметров и цены в записи), 0008 (транзиентный выбор)

## Контекст

В схеме была таблица `cars` (карточка автомобиля клиента: госномер, радиус, тип, опции) — источник параметров при записи. Реальный прайс показал: опции не параметры; параметры (радиус/тип) и госномер нужны записи как снимок, а не справочник клиента. Карточка авто плодила дубли (несколько машин клиента, правки задним числом), а подстановка «при повторной записи» требовала связности, которой нет у гостя.

## Решение

Сущность «автомобиль» **упразднена**: `cars` удалена, `bookings.car_id` заменён на `bookings.plate` (nullable, госномер из заявки). Параметры авто (радиус, тип) и госномер — **снимок записи** (ADR 0004). При повторной записи оператор (ФТ-18) подставляет госномер и параметры из последней записи клиента. Демо-сид моделирует это «профилем» параметров клиента в памяти.

## Почему (альтернативы)

- Карточка авто как справочник клиента: требует создания/выбора машины при записи гостя, допускает дубли и рассинхрон с фактической записью; для v1 (без личного кабинета) не окупается.
- Хранить параметры только в заявке-выборе без снимка: история записей потеряла бы параметры/номер.
- Цена: простота схемы и создания записи; повторная запись чуть менее удобна (нет «списка авто клиента» в админке), но покрывается последней записью.

## Последствия

Проще: создание записи (в т.ч. админкой) без машины; история самодостаточна (снимки). Сложнее: админка не показывает «автопарк клиента» — при появлении личного кабинета или нескольких авто на клиента сущность вернётся (отдельный ADR). Пересмотр: если админке понадобится группировка по автомобилю/госномеру — вернуть справочник с привязкой.
